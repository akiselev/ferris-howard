# FH Codegen: Proven Rust Out, Clean Lean Out

**Status:** Draft 0.1 · Design for the two export directions: `fh emit-rust` (verified executable code from the FH/Lean development) and `fh emit-lean` (publication-grade Lean artifacts with zero FH dependency). One architectural amendment to M0 falls out and is flagged below.

## 0. The 2026 landscape (researched, not recalled)

Three facts shape everything. **(1) Rust→Lean is production-grade.** The Charon/Aeneas and Hax pipelines lift safe Rust into pure Lean 4 (Aeneas via the LLBC borrow calculus, each function landing in a `Result` monad; used at scale in the zkEVM verification world, with kernel-checked proofs over extracted models of Plonky3/RISC Zero primitives). Known edges are documented: a finite supported fragment (iterator-heavy and deeply generic code excluded; the pure, bounded-loop fragment is the reliable core) and real toolchain-drift pain across Aeneas/Hax/Mathlib pins. **(2) Lean→Rust *verified* extraction now exists.** The Peregrine project provides a unified, Rocq-verified middle-end from proof assistants (Agda, Lean, Rocq) to CakeML/C/Rust/OCaml via λ□ — MetaCoq's erased lambda-calculus IR — with the Lean-side `Expr` → λ□ erasure bridge implemented. Verified extraction to Rust from Lean is no longer hypothetical; its maturity and performance envelope are the open questions, not its existence. **(3) The adjacent genre is active** (equality-saturation optimizers emitting C/Rust from Lean specs with proof traceability), so the community's direction of travel matches ours.

## 1. Direction A — `fh emit-rust`: three lanes, one trust story

**Lane R1 — syntactic projection (the FH-specific gift).** FH's computational `fn`s are *already Rust surface syntax*: the projection for the executable fragment is nearly the identity — strip proofs and `Prop`-typed arguments, erase dependent indices (or reify them as debug asserts), and map the numeric spine through a fixed data-refinement table (`Nat/Int/Rat` → `BigUint/BigInt/BigRational`; `Fin n` → bounded ints **with the bound theorem justifying the machine type** — proof-carrying data refinement, the classical extraction subtlety made explicit). Output: idiomatic, fast, human-auditable Rust. Trust: none required from the printer — see R3.

**Lane R2 — the Peregrine lane.** Elaborated Lean → λ□ → verified middle-end → Rust backend. The high-assurance reference path: semantics preserved by a machine-checked compiler pipeline. Costs to scope by spike: backend maturity, boxed/RC performance, numeric-representation control. Use: reference builds of the checkers, cross-validation oracle for R1, and the long-run answer if it matures well.

**Lane R3 — translation validation by round-trip (the keystone).** Whatever Rust we emit — R1's idiomatic code, even hand-optimized variants — run the *mature reverse direction* on it: Charon+Aeneas lift the emitted Rust back into pure Lean, and we prove, in Lean, that the lifted model is extensionally equal to the original FH-elaborated function. Per-artifact equivalence theorems instead of a trusted extractor: the emitted code arrives with a kernel-checked certificate that it computes the verified function. This is the house style — *emit dirty, certify by round-trip* — and it converts the ecosystem's asymmetry (Rust→Lean mature, Lean→Rust young) into an advantage: the mature direction becomes the checker for the young one. Discipline it imposes: emitted Rust must stay inside Aeneas's reliable fragment — pure functions, bounded loops, no iterator gymnastics — which is *exactly the shape of certificate-checking code anyway*; the style guide writes itself.

**The first customer, chosen for maximal self-benefit:** extract the certified certificate checkers — the LDLᵀ validator, interval evaluators, exhaustion checkers. Today the pipeline maintains two implementations (fast Rust for search-side pre-validation, Lean for kernel truth) with a semantic gap between them; extraction with R3 round-trip *unifies them*: the Rust searcher pre-validates candidates with literally-the-same-verified logic the kernel will accept, dual maintenance ends, and the program gains verified high-performance numerical kernels as a side effect. Every later track (plasma δW, RDM brackets, KAM checks) inherits the unification for free.

## 2. Direction B — `fh emit-lean`: the publication artifact

**Goal:** a referee, a Mathlib maintainer, or a journal never needs to know FH exists. The emitted artifact is self-contained Lean 4 + Mathlib, idiomatic, readable, and *provably equivalent* to what we developed.

**The architectural amendment (binding on M0):** implement FH constructs as **syntax→syntax macros** (`macro_rules` expanding to Lean *surface* syntax) wherever possible, reserving `elab_rules` for the few constructs that genuinely need elaborator access — because then `emit-lean` is one macro-expansion step plus a formatter, and faithfulness is *by construction* rather than by delaboration heroics (Lean's `Expr`-level pretty-printing round-trips are notoriously lossy; surface-level expansion sidesteps the entire problem). This amends the design doc's original "two-stage lowering" preference from soft to load-bearing: the printable middle stage *is* the publication artifact.

**The pipeline:** expand once → format (Mathlib style: naming conventions, `theorem`/`lemma` choices, spacing linters) → preserve doc comments and attribution headers → resolve the prelude. Prelude policy is the honesty crux: the FH support library must be **zero-runtime by design** — every emitted file imports Mathlib only, with FH's small class/lemma prelude either (a) inlined per-file, (b) vendored as one tiny MIT `FHCore.lean` the artifact includes, or (c) progressively upstreamed to Mathlib until the prelude is empty. Track (c) is the strategic one: each upstreamed prelude lemma makes every future artifact thinner.

**The guarantee — the round-trip gate:** CI re-elaborates the emitted Lean from scratch and checks every declaration against the direct FH elaboration — same statements (hash-frozen, per H2 discipline), definitionally equal terms — then runs `lean4checker` on the emitted artifact alone. The published file is thereby *proven* to mean what we proved, and FH drops out of the trusted base entirely: it becomes invisible authoring tooling, the TypeScript-to-readable-JS relationship, with the equivalence itself kernel-checked. Failure honesty: constructs that can't survive surface expansion (elab-only features, hygiene-mangled names) are either given custom expanders or **banned from the publishable subset** by lint — an "emittable" lint gate keeps the corpus inside the exportable fragment from day one.

## 3. Milestones and risks

**E1 (with M0):** syntax→syntax discipline adopted; `emit-lean` on the statement layer; round-trip gate in CI. **E2 (with P1's Phase 3):** the LDLᵀ checker extracted via R1, certified via R3 round-trip — the pipeline's validators unified. **E3 (parallel spike):** Peregrine lane evaluated on the same checker; performance and maturity report to the ledger. **Risks, named:** toolchain drift is the ecosystem's documented tax (Aeneas/Hax/Mathlib pins diverge; the experience-report literature says budget real coordination time) — pin everything, vendor what we must; Aeneas-fragment limits constrain emitted-Rust style — acceptable, since checker code fits the fragment naturally; Peregrine performance may disappoint — R1+R3 carries the program regardless, with R2 as the deepening trust story rather than the critical path.

The strategic summary: FH's Rust-flavored surface makes Lean→Rust *cheap* (the code already looks like Rust), the mature Rust→Lean tooling makes it *certifiable* (round-trip validation), the new verified middle-end makes it *deepenable* (Peregrine), and syntax-level macro discipline makes the Lean side *publishable with zero toolchain trust*. Both exports land without inventing a compiler — the ecosystem built our missing halves while we were designing the middle.

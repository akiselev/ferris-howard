# Ferris–Howard Agent Layer: Proof Execution, Debugging, REPL

**Status:** Draft 0.2 (amended 2026-08-01) · Companion to design doc and corpus review.
**Purpose:** give AI agents (Claude Code instances et al.) a tight loop for writing, running, and debugging FH/Lean proofs — and a hardened verification path so that a claimed proof of an open problem is *actually* a proof.

## 1. Components

**`fh check` — batch elaboration with machine-readable diagnostics.** Wraps `lake build` / `lake env lean` over FH sources (FH-in-`.lean` files through M2; a standalone `.fh` form arrives with M3 — design doc §2). Output is JSON: per-declaration status (elaborated / error / sorry), error messages with *FH-source spans* (the source-map from macro expansion is what makes this useful — an agent must never debug against generated Lean positions), the goal state at every `sorry`/`todo!()`, the axiom footprint of every completed proof (`#print axioms`, mechanically), and the role/binding metadata of design doc §4.9 (object roles as written, binding roles as computed — the machine-readable variable taxonomy). This is the workhorse: 90% of an agent's loop is edit → `fh check` → read goals → edit.

**`fh repl` — interactive proof states.** Wrap the community Lean REPL (`leanprover-community/repl`: JSON-over-stdio, supports submitting commands against a persistent environment, running tactics against saved proof states, and pickling/unpickling environments for cheap forking). The FH layer adds: accept FH-syntax declarations (translate, submit, map diagnostics back), and expose proof states as first-class handles so an agent can *fork* a state, try three tactics in parallel, and keep the winner. Pantograph is the fallback/upgrade if we need finer-grained goal manipulation than the REPL exposes. Design rule: the REPL is for *exploration*; nothing counts until it re-elaborates from source via `fh check` — REPL environments accumulate state that can mask errors. (Upstream labels tactic mode experimental and lists pickle improvements as future work — that status is part of why this rule exists.)

**`fh mcp` — the agent-facing surface.** An MCP server exposing: `elaborate(file)`, `goals(file)` (all sorry-sites with pretty-printed goals, local contexts, and binding-role annotations), `try(state, tactic) -> new_state | error`, `search(query)` (fan out to Loogle's API for type-directed search, LeanSearch for natural-language, and local `exact?`/`apply?`/`rw?` invocations against the current goal — Mathlib retrieval is the single highest-leverage tool for proof-writing agents), `minimize(file, decl)` (bisect a failing proof to a minimal repro), and `status()` (build health, cache warmth). Rationale for MCP rather than bare CLI: uniform across your agent-swarm-cli orchestration, and tool-call transcripts become auditable artifacts.

**Environment engineering.** Mathlib's build is the tax on everything: pin the toolchain, pull olean caches (`lake exe cache get`), keep a warm daemon per worker, hard timeouts per tactic (default 20s heartbeat-equivalent) and per file. Parallel agents get isolated worktrees but a shared read-only Mathlib cache. Budget note: a cold Mathlib build is *hours* — avoid it entirely, always pull the olean cache; a warm check of one file is seconds — the entire agent-loop economics live in keeping things warm. Scheduling (2026-08-01): the minimal `fh check` lands with design-doc milestone M1 (its span infrastructure is emitted while the macros are written and painful to retrofit); `fh repl` and `fh mcp` land with M2.

## 2. The debugging feedback design

Errors are the curriculum. Three refinements beyond raw Lean errors, all cheap: (1) classify errors into a small taxonomy agents can branch on — unknown identifier (→ call `search`), type mismatch with coercion-shaped diff (→ suggest `as` insertion; our explicit-coercion ruling makes these common and mechanical), unsolved goals (→ return the goals), Decidable-instance-missing (→ our F14, with the fixed wording), deterministic timeout (→ suggest `simp` → `simp only` narrowing). (2) On `simp` success, offer `simp?`'s minimized lemma list back to the agent so proofs get committed in maintainable form. (3) On failure of a whole proof, auto-run the counterexample battery (below) against the *statement* — the most valuable debugging information is "you are trying to prove something false."

## 3. The disproof arm

Half the recent AI wins are counterexamples, so falsification is a first-class pipeline, run *before* serious proof effort on any target: `plausible` (Mathlib's property-based random tester, née slim_check) against the FH statement and its instantiations; `decide`/`native_decide` for finite or bounded fragments; and unverified-but-fast search *outside* Lean (your Rust — enumerate structures, SAT/SMT encodings) with any found candidate then *verified inside* Lean via `decide` or explicit construction. The Rust-side searcher is where your background is an unfair advantage; the Lean side is what makes a found counterexample a theorem rather than a claim.

## 4. Anti-cheat verification protocol

Agents under optimization pressure find backdoors; the protocol assumes so. A result claims "proved" only if ALL of: (a) clean `fh check` from source in a fresh environment — no REPL state; (b) zero `sorry` in the transitive proof; (c) axiom audit passes a whitelist (`propext`, `Classical.choice`, `Quot.sound` and nothing else — no `native_decide`'s `ofReduceBool` unless explicitly accepted for that result, no stray `axiom` declarations smuggled into imports); (d) *statement-unchanged check*: the formal statement is frozen (hash-pinned) before proof attempts begin, and the final theorem's statement must be definitionally identical — this kills the classic failure where an agent "proves the theorem" by quietly weakening it; (e) independent kernel recheck of the produced olean via `leanchecker` (formerly the standalone `lean4checker`, shipped with the Lean toolchain since v4.28; it replays the environment through Lean's kernel, so the trusted base still includes that kernel — which matches this protocol's goal of excluding only the FH toolchain; if full kernel-independence is ever wanted, the escalation path is `lean4export` plus an external checker). Steps (c)–(e) exist because the trusted base must exclude our entire FH toolchain: FH macros could be buggy, so what gets audited is the *elaborated Lean term*, not our syntax.

## 5. Open-problem workflow

Step 0, always: re-verify the problem is still open — erdosproblems.com page status, the AI-contributions wiki, arXiv search within the last 90 days. The field is moving at a pace where a month-old "open" is stale. Step 1: obtain or write the formal statement — prefer importing an existing formalization (DeepMind's Formal Conjectures repo; erdosproblems' own formalization efforts) over writing our own, since a statement-formalization error invalidates everything downstream; if we formalize, the FH statement plus its Lean expansion both get human review before freezing. Step 2: falsification battery (§3). Step 3: proof attempts — decompose into lemma DAG, farm lemmas to parallel agents via the MCP surface, integrate. Step 4: for any success, run §4, then produce the human-readable writeup (the community expects prose + Lean, not Lean alone), then follow the wiki's submission etiquette ("what to do when you think AI solved an Erdős problem" — post to the problem's discussion, disclose AI involvement, invite literature check: several past "solutions" turned out to already exist in the literature, which is a deflating but survivable outcome).

## 6. Honesty clauses

Two, built into the tooling's report format. Every result report states the AI systems used, the human involvement, and the literature-search performed — matching the wiki's classification scheme (standalone / alongside literature / building on literature / collaborating). And every "proved" banner carries the axiom list and the statement hash, so a third party can audit without trusting us. The credibility of an AI-proof project *is* its verification protocol; we ship the protocol as part of the result.
